# FR-005 集成 llama.cpp Submodule，替换 STUB 模式，实现真实 GGUF 加载

**创建日期**：2026-06-09
**状态**：Active
**Feature**：fr-005-llama-cpp-submodule

---

## 1. 业务上下文

- **谁会用**：Android LLM 推理助手的开发者与端侧推理消费者。
- **解决什么问题**：FR-004 构建了完整的 GGUF 模型加载接口，但 `libllama_jni.so` 当前以 STUB 模式编译（返回固定指针 `0xC0FFEE`），无法完成真实的模型推理。llama.cpp 作为第三方库以 git submodule 方式管理，尚未初始化，导致 JNI 层调用路径未经过真实 C++ 代码验证。
- **价值**：完成 submodule 集成后，`libllama_jni.so` 将链接真实的 llama.cpp，`loadModel(path)` 调用会通过 `llama_load_model_from_file` 读取 GGUF 文件并返回有效 native 指针。这是端侧推理能力的基础，后续推理 UI 与 token 生成均依赖此层。

---

## 2. 功能需求

### FR-005-1 llama.cpp 以 git submodule 方式集成

在 `android-llm-app/third_party/llama.cpp` 路径下添加 llama.cpp submodule，锁定至经过验证的稳定提交（tag `b4530` 或更新的兼容版本）。

**验收标准**：
- AC1：`.gitmodules` 中存在 `[submodule "android-llm-app/third_party/llama.cpp"]` 条目，url 指向 `https://github.com/ggerganov/llama.cpp`。
- AC2：`git submodule status` 显示 submodule 已初始化（`+` 或空格前缀），不显示 `-`（未初始化）。
- AC3：submodule 锁定到具体 commit SHA（不跟踪 HEAD），确保构建可复现。

### FR-005-2 CMakeLists.txt 切换为真实模式

当 `android-llm-app/third_party/llama.cpp/CMakeLists.txt` 存在时，CMake 构建使用 `add_subdirectory` 链接 llama.cpp，不再以 STUB 编译 `libllama_jni.so`。

**验收标准**：
- AC1：`./gradlew assembleDebug` 在 submodule 已初始化的环境下成功产出链接了真实 llama.cpp 的 `libllama_jni.so`。
- AC2：CMake 输出（`cmake --build` verbose）不出现 `Building llama_jni in STUB mode` 警告。
- AC3：现有 STUB 降级逻辑保留（submodule 未初始化时仍以 STUB 模式编译），以保持开发者不强制拉取 submodule 时也能编译通过。

### FR-005-3 llama_jni.cpp 实现真实 GGUF 加载路径

`llama_jni.cpp` 在 `LLAMA_CPP_AVAILABLE=1` 宏下，调用 `llama_load_model_from_file(path, params)` 加载 GGUF，并在 `freeModel` 中调用 `llama_free_model(model)`。

**验收标准**：
- AC1：`Java_com_harnessclaude_llm_nativebridge_LlamaJni_loadModel` 在真实模式下调用 `llama_load_model_from_file`，返回指向 `llama_model*` 的 `jlong` 指针（非 `0xC0FFEE`）。
- AC2：`Java_com_harnessclaude_llm_nativebridge_LlamaJni_freeModel` 在真实模式下调用 `llama_free_model(reinterpret_cast<llama_model*>(ptr))`。
- AC3：加载 GGUF magic bytes 校验（`0x46554747`）逻辑在真实模式下仍保留，防止加载非 GGUF 文件进入 C++ 层。

### FR-005-4 包含 GGUF Fixture 的 Instrumented 测试

在 `androidTest` 中添加一个可在连接真机/模拟器时运行的 instrumented 测试，使用最小 GGUF fixture（约 1–5 MB，仅含必要 header 与少量 tensor）验证真实加载路径。

**验收标准**：
- AC1：`app/src/androidTest/assets/` 目录下存在至少一个 `.gguf` 测试 fixture（可为 TinyLlama 1.1B Q2_K 或其他 ≤ 5 MB 的合法 GGUF）。
- AC2：`LlamaCppLoaderInstrumentedTest.loadModel_returnsValidHandle` 在 `connectedAndroidTest` 下返回 `nativePtr != 0` 且 `nativePtr != 0xC0FFEE`。
- AC3：测试结束后 `handle.close()` 被调用，不发生 native 内存泄漏（通过 LeakCanary 或 AddressSanitizer 验证，或 logcat 无 `SIGSEGV/double-free` 输出）。

## 4. 排除范围

- **llama.cpp token 生成 / 推理接口**：本 FR 仅完成模型加载（`loadModel` / `freeModel`），不实现 `eval`、`sample` 或流式推理。
- **多 ABI 支持**：仍仅支持 `arm64-v8a`，不新增 `x86_64` / `armeabi-v7a`。
- **GPU 后端（Vulkan / OpenCL）**：仅 CPU 推理路径，不启用 GGML GPU 加速后端。
- **CI connectedAndroidTest 配置**：instrumented test 存在即满足需求，CI pipeline 接入属于独立基础设施 FR。
- **模型下载 UI**：用户如何获取 GGUF 文件属于后续 UI FR，本期不涉及。
- **llama.cpp 版本升级策略**：选定 commit 后锁定，版本升级策略属于维护期工作。

## 5. 依赖与影响范围

**上游依赖**（本功能需要什么）：
- `android-llm-app/third_party/llama.cpp`：llama.cpp git submodule（ggerganov/llama.cpp，pinned commit）
- NDK r25b 或 r26b（Clang 14+），已在 `local.properties` / CI 中配置
- `LlamaJniBridge` 接口（FR-004 已实现，无需改动）
- `llama_jni.cpp` STUB 模式代码（需替换真实路径逻辑）

**下游影响**（本功能改动会影响什么）：
- `android-llm-app/app/src/main/cpp/CMakeLists.txt`：新增 `add_subdirectory(third_party/llama.cpp)`
- `android-llm-app/app/src/main/cpp/llama_jni.cpp`：`LLAMA_CPP_AVAILABLE=1` 宏下实现真实调用
- `android-llm-app/app/src/androidTest/`：新增 GGUF fixture 与真实 instrumented 测试
- `.gitmodules`：新增 submodule 条目
- `gatekeeper-checks.sh`：submodule 初始化状态检查（可选增强）

**变更范围**：替换 STUB + 新增 submodule + 扩展 instrumented 测试。
