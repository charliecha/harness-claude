## 4. Warning 问题

### W-005-1：`llama_backend_init` / `llama_backend_free` 每次加载/释放各调一次

**文件**：`android-llm-app/app/src/main/cpp/llama_jni.cpp:67, 96`

当前实现在每次 `loadModel` 调用时执行 `llama_backend_init()`，每次 `freeModel` 时执行 `llama_backend_free()`。llama.cpp 内部将 `llama_backend_init` 实现为幂等（多次调用安全），但 `llama_backend_free` 文档未明确说明多次调用行为。在单模型场景下无影响；多模型并发加载时若有两个 freeModel 同时执行，`llama_backend_free` 可能被调用多次。

**处理决定**：接受，单模型场景无实际问题。推理 FR 中实现多模型并发时，将 backend 生命周期提升至 `JNI_OnLoad` / `JNI_OnUnload` 管理。

### W-005-2：GGUF fixture 仅含 header，不含 tensor 数据

**文件**：`android-llm-app/app/src/androidTest/assets/tinyllama-test.gguf`

`tinyllama-test.gguf`（640 bytes）仅含合法 GGUF header 和 KV metadata，tensor_count=0。`llama_model_load_from_file` 能成功返回非 NULL 指针（加载成功），但该模型无法进行实际推理（无 embedding weights）。instrumented 测试断言 `nativePtr != 0 && != 0xC0FFEE` 即告通过，验证了真实 JNI 加载路径，但不能验证推理正确性。

**处理决定**：接受。本 FR 范围为加载路径验证，不涉及推理。推理 FR 需替换为真实可推理 GGUF fixture（如 TinyLlama 1.1B Q2_K，需 CI seed）。

### W-005-3：gatekeeper-checks.sh 扫描排除了整个 `third_party/` 目录

**文件**：`.harness/packs/kotlin/gatekeeper-checks.sh`

为排除 llama.cpp 示例代码中的 `!!` / `GlobalScope` / `println`，所有 grep 命令加入了 `--exclude-dir=third_party`。这意味着若未来在 `third_party/` 下添加项目自有代码（非 submodule），也将被静默跳过。

**处理决定**：接受。`third_party/` 按约定专属于第三方代码，不应放置项目代码。记录为约定（convention over configuration）。

## 5. Info 问题

### I-005-1：使用新版 API 替换了 deprecated 函数

`llama_jni.cpp` 中 `llama_load_model_from_file` → `llama_model_load_from_file`，`llama_free_model` → `llama_model_free`，消除了 b4999 版本中的 `-Wdeprecated-declarations` 警告。这是良好的前向兼容实践。

### I-005-2：CMakeLists.txt 新增 generator expression include 路径

`target_include_directories` 中 `$<$<BOOL:${LLAMA_CPP_AVAILABLE}>:${LLAMA_CPP_DIR}/include>` 使用 CMake generator expression 确保仅在真实模式下添加 include 路径，STUB 模式不引入未使用的路径。llama target 本身已通过 PUBLIC include 传递 `include/`，此处为防御性重复声明，无负面影响。
