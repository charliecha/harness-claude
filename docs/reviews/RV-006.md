## 3. Critical 问题（必须修复）

**Critical 问题数**：0

已扫描的维度及结论：

- **资源泄漏**：`InferenceSession.close()` 使用 `synchronized(lock)` 正确释放 `ctxPtr`；`InferenceViewModel.onCleared()` 调用 `session?.close()` 和 `modelHandle?.release()`；`sampleNext` C++ 侧使用 `llama_sampler_free(chain)` 在返回前释放采样器链。无泄漏。
- **错误处理**：无裸 `catch: pass` / `catch (e: Exception) {}` 吞异常。`generate()` 的 `finally` 块确保 `generating.set(false)` 在所有分支执行。ViewModel 的 `.catch {}` 显式更新 UiState error 字段，不吞异常。
- **并发安全**：`AtomicBoolean generating` 通过 `compareAndSet(false, true)` 防止并发 `generate()` 调用；`close()` 通过 `synchronized(lock)` 防止 double-free；`ctxPtr` 标注 `@Volatile` 确保跨线程可见性。
- **内部错误泄漏**：`InferenceError.DecodeFailed(code)` 只暴露整数退出码，不含 C++ 内部路径或地址；日志通过 Timber，不打印 prompt 内容；UI 层只显示 `e.message`，信息受控。
- **硬编码密钥**：全代码库扫描无硬编码凭证（gatekeeper Kotlin 安全检查通过）。
- **smoke_test.sh 覆盖缺口**：`scripts/smoke_test.sh` 是针对 Python `crypto_price_feed` 库及 FastAPI HTTP 层的集成冒烟测试，与 Android Kotlin 模块无关。FR-006 交付的是 Android 端侧库，无 HTTP/CLI 对外接口；其"对外接口"通过 Android JUnit 单元测试（`testDebugUnitTest`）和 Gradle 构建验证覆盖，不存在可被 shell 脚本调用的服务端点。此项不构成 Critical。

## 4. Warning 问题（建议修复，须说明处理决定）

### W-001 `InferenceSession` 缺少 `usedTokens` 属性（FR-006-1 AC3 部分未满足）

**文件**：`android-llm-app/app/src/main/java/com/harnessclaude/llm/inference/InferenceSession.kt`（类定义，约第 15 行）

FR-006-1 AC3 要求 `InferenceSession` 暴露 `usedTokens: Int`（已使用 token 数）只读属性。当前实现仅有 `contextSize` 和 `isReleased`，`usedTokens` 未实现。`usedTokens` 需追踪 KV cache 已使用的 token 槽位数，在 multi-turn 场景下有实用价值（判断是否接近 context 上限）。

**处理决定**：下迭代处理。当前 multi-turn 场景为实验性（ADR-006 TODO-006-5 已记录 context 溢出风险），`usedTokens` 的精确追踪需要额外 JNI 方法（`llama_get_kv_cache_used_cells`）。首版不阻塞交付，在 context shifting FR 中一并实现。

---

### W-002 `generate()` 日志中 `tokenCount` 恒等于 `params.maxNewTokens`，实际生成数未记录

**文件**：`android-llm-app/app/src/main/java/com/harnessclaude/llm/inference/InferenceSession.kt`，第 44、56 行

```kotlin
var tokenCount = 0
// ...（finally 之外）
tokenCount = params.maxNewTokens  // 行 56：EOG 提前终止时此值不反映实际生成数
```

`generateLoop()` 内部有独立的 `generated` 变量并打印了实际生成数（行 89），但外层 `tokenCount` 始终被赋值为 `maxNewTokens`，导致 `finally` 块的 tokens/s 计算在 EOG 提前停止时失真（NFR-006-5 可观测性要求存在偏差）。

**处理决定**：本轮处理建议。修复方式：将 `generateLoop()` 的返回值改为实际生成数，赋给 `tokenCount`。修改量极小且不影响行为。

---

### W-003 `InferenceViewModel.generate()` 中旧 session 关闭时序存在短暂资源重叠

**文件**：`android-llm-app/app/src/main/java/com/harnessclaude/llm/viewmodel/InferenceViewModel.kt`，第 76-79 行

```kotlin
val sess = sessionFactory.create(handle, params)  // 新 session 创建（新 ctxPtr 已分配）
session?.close()   // 旧 session 关闭（若这一行之前异常则旧 session 泄漏——但 create 在这行之前完成，无异常路径）
session = sess     // 引用替换
```

当前顺序：先创建新 session，再关闭旧 session，再更新引用。若 `session?.close()` 和 `session = sess` 之间发生协程取消（`CancellationException`），旧 session 的 `freeContext` 已调用，不会泄漏，但 `session` 字段仍持有旧（已释放）引用直到 `onCleared()`。`onCleared()` 中 `session?.close()` 会对已释放 session 调用 `close()`，由于 `close()` 幂等（`ctxPtr == 0L` 时直接返回），不会 double-free。实际上无泄漏，但顺序可读性差。推荐顺序：先关旧，再创新，再赋引用。

**处理决定**：下迭代处理。当前无资源安全问题（`close()` 幂等保护），重构时一并整理。

---

### W-004 `concurrent generate calls` 测试未实际验证并发路径

**文件**：`android-llm-app/app/src/test/java/com/harnessclaude/llm/inference/InferenceSessionTest.kt`，第 180-203 行

测试方法名为 `concurrent generate calls throw ConcurrentGeneration`，但实现仅验证了正常路径（单次调用成功完成），注释也承认"Cannot easily test real concurrency in unit context"。`AtomicBoolean` 保护的并发路径实际上未被测试覆盖；若 `generating` 已为 `true` 时调用 `generate()`，测试无法验证是否确实抛出 `ConcurrentGeneration`。

**处理决定**：下迭代处理。可通过以下方式修复：在 `generate()` 执行完成前，在同一协程作用域内启动第二个 `launch` 并捕获异常；或直接在测试中通过反射/mock 强制 `generating` 为 `true` 后调用 `generate()`。

---

### W-005 `check(!handle.isReleased) { throw InferenceError.HandleReleased() }` 使用非标准 `check` 惯用法

**文件**：`android-llm-app/app/src/main/java/com/harnessclaude/llm/inference/InferenceSessionFactory.kt`，第 18 行；`InferenceSession.kt`，第 37、38 行

`check(condition) { throw SomeException() }` 的 lambda 本意是提供 `String` 消息，此处直接抛出异常。功能上是正确的（lambda 抛出后 `IllegalStateException` 包装不会执行，自定义异常直接向上传播），但这是 Kotlin `check` 的非标准用法，阅读者容易误解为 lambda 返回消息字符串。Kotlin 规范写法是直接 `if (!condition) throw SomeException()`。

**处理决定**：下迭代处理。建议在下次重构时替换为直接 `if` 抛出，以提升代码可读性并消除歧义。

## 5. Info 问题（供参考）

### I-001 KV cache 在同一 `InferenceSession` 多次 `generate()` 调用间不清空（设计决定）

ADR-006 §5 明确决策：同一 session 每次 `generate()` 不清空 KV cache，以支持 multi-turn 追加语境（FR-006-3 AC5）。`clearKvCache()` JNI 方法已实现，但在 `generate()` 中未调用。ADR-006 TODO-006-5 已记录 context 窗口溢出风险。此为已知设计权衡，非缺陷。

---

### I-002 STUB 模式下 `tokenize` 返回空数组导致 `generate()` 立即返回

`llama_jni.cpp` 第 191-193 行：STUB 模式下 `tokenize` 返回空 `IntArray(0)`。`InferenceSession.generate()` 第 47 行：`if (promptTokens.isEmpty()) return@channelFlow`。这导致 CI 单元测试中（mock JNI bridge）若未正确 stub `tokenize` 返回值，Flow 会静默完成而不报错。现有测试均正确 stub 了 `tokenize`，但这是潜在的测试陷阱。

---

### I-003 `sampleNext` 每次调用创建并销毁一个 `llama_sampler_chain`，性能次优

`llama_jni.cpp` 第 259-271 行：每次 `sampleNext` 调用都执行 `llama_sampler_chain_init` + 三次 `chain_add` + `llama_sampler_free`。在高频 token 生成场景下（≥ 3 token/s），反复分配/释放采样器链会产生不必要开销。ADR-006 TODO-006-3 已记录性能优化 TODO，此项与之相关。建议后续将 sampler chain 的生命周期绑定到 `InferenceSession` 或 `generate()` 调用周期。

---

### I-004 `InferenceViewModel` 中 `generateJob` 取消后 `isGenerating` 状态可能短暂不一致

`InferenceViewModel.stopGeneration()`（第 110-114 行）调用 `generateJob?.cancel()` 后立即设置 `isGenerating = false`。然而 Flow 的 `collect` lambda 在取消后可能还有一次 `_uiState.update { it.copy(isGenerating = false) }`（第 100 行）执行，即状态会被冗余设置两次。这是无害的幂等操作，但属于轻微的状态管理冗余。
